# DSA Problem Generator Using a Locally Hosted LLM

A college mini-project that generates customized Data Structures and Algorithms (DSA) problems using a locally running Large Language Model (LLM) — no external APIs, no internet required after setup.

---

## Quick Start

```bash
# 1. Create and activate a virtual environment (recommended)
python -m venv venv
venv\Scripts\activate          # Windows
# source venv/bin/activate     # macOS/Linux

# 2. Install dependencies
pip install -r requirements.txt

# 3. Run the app (downloads model ~3 GB on first run)
streamlit run app.py

# 4. Run evaluation experiments
python evaluation.py
```

The requirements install a CUDA 13.0-enabled PyTorch build for NVIDIA GPUs.
The model is placed on the NVIDIA GPU when CUDA is available; otherwise it
runs on the CPU. Verify the CUDA-enabled install with:

```bash
python -c "import torch; print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0) if torch.cuda.is_available() else 'CPU')"
```

Generated output is checked before it is shown. Python test cases accept either
a runnable script or a single-function solution; generated expected outputs
still need human review because LLM-generated problems and solutions are not
guaranteed to be correct. Local generation runs token by token, so it can take
several seconds even after the model has loaded. Python test comparisons ignore
whitespace differences, as programming judges typically do, but still require
the same output values and order.

## What Each File Does

| File | Purpose |
|------|---------|
| `app.py` | Streamlit web UI. Collects user inputs, calls other modules, displays results. |
| `model.py` | Loads Qwen2.5-Coder-1.5B-Instruct using `AutoTokenizer` + `AutoModelForCausalLM`. Runs `model.generate()`. |
| `prompt_builder.py` | Constructs the system + user message sent to the LLM. Embeds grounding context. |
| `grounding.py` | Reads `problem_bank.json` and returns relevant facts for the selected topic. |
| `validator.py` | Parses and validates model output, normalizes test data, and runs Python scripts or function solutions. |
| `evaluation.py` | Runs experiments comparing temperatures 0.1, 0.3, 0.7. Saves results to JSON. |
| `problem_bank.json` | Verified DSA facts: descriptions, complexities, constraints, edge cases per topic. |

## Viva Questions and Answers

### 1. What is an LLM?

A Large Language Model (LLM) is a neural network trained on massive amounts of text to predict the next token in a sequence. By doing this at scale, it learns grammar, facts, reasoning patterns, and code. Examples: GPT-4, Llama, Qwen. The "large" refers to the number of parameters — Qwen2.5-Coder-1.5B has 1.5 billion parameters.

### 2. Why does this project qualify as an LLM project?

The core output — problem statements, solutions, test cases, explanations — is generated by a real LLM (Qwen2.5-Coder-1.5B-Instruct) running locally. The LLM is not replaced by templates or hardcoded strings. The project uses `AutoModelForCausalLM`, `apply_chat_template()`, and `model.generate()` from Hugging Face Transformers, which are standard LLM inference tools.

### 3. Which model is used and why?

**Qwen2.5-Coder-1.5B-Instruct** by Alibaba Cloud.

- "Coder" variant: fine-tuned specifically on code, making it better at generating correct solutions.
- "Instruct" variant: fine-tuned with instruction-following (RLHF/SFT), so it follows structured prompts reliably.
- 1.5B parameters: small enough to run on a laptop CPU (slowly) or a mid-range GPU, making it practical for a college project.
- Freely available on Hugging Face with no API key required.

### 4. What are model parameters?

Model parameters are the learned weights (numbers) inside the neural network — the values in weight matrices that were adjusted during training. Qwen2.5-Coder-1.5B has ~1.5 billion such numbers. These are fixed after training and stored in the model files you download.

### 5. Difference between model parameters and generation parameters?

| | Model Parameters | Generation Parameters |
|---|---|---|
| What | Learned weights inside the neural network | Settings that control how text is sampled |
| When set | During training (fixed after) | At inference time (you control these) |
| Examples | Weight matrices W1, W2, ... | temperature, top_p, max_new_tokens |
| Size | 1.5 billion numbers | A handful of values |

### 6. What is Temperature?

Temperature controls randomness in token selection. After the model computes a probability distribution over all possible next tokens, temperature scales it:

- **Low temperature (0.1):** Distribution becomes sharper — the highest-probability token is almost always chosen. Output is deterministic and repetitive.
- **High temperature (0.9):** Distribution becomes flatter — lower-probability tokens get more chance. Output is creative but may be incoherent.
- **Our default (0.3):** Slightly creative but mostly consistent — good for structured JSON output.

### 7. What is Top-p (Nucleus Sampling)?

Instead of considering all tokens, top-p sampling keeps only the smallest set of tokens whose cumulative probability exceeds p. With `top_p=0.9`, the model only samples from tokens that together account for 90% of the probability mass. This cuts off very unlikely tokens while preserving diversity.

### 8. What are Max New Tokens and Context Window?

- **Max new tokens:** The maximum number of tokens the model is allowed to generate in one call. We use 1500.
- **Context window:** The maximum total tokens (input + output) the model can process at once. Qwen2.5-Coder-1.5B has a 32K token context window. If input + output exceeds this, the model truncates or behaves unpredictably.

### 9. What are Tokens?

Tokens are the basic units the model processes — not characters, not words, but subword pieces. "programming" might be one token; "unbelievable" might be split into "un", "believ", "able". On average, 1 token ≈ 0.75 English words. Tokenization is done by the tokenizer (e.g., `AutoTokenizer`).

### 10. What is Grounding / RAG?

**RAG (Retrieval-Augmented Generation)** means augmenting the LLM's prompt with retrieved external information before generating.

In this project:
1. User selects "Arrays" + "Medium"
2. `grounding.py` reads `problem_bank.json` and retrieves: description, concepts, constraints for Medium, expected complexity, common edge cases
3. This text is prepended to the LLM prompt
4. The LLM uses these verified facts when generating the problem

**Why it helps:** The LLM may hallucinate wrong complexities (e.g., claim O(n²) when O(n) is expected). By injecting the correct complexity from our knowledge base, we guide the model toward accurate output.

**Limitation:** Grounding reduces hallucinations but does NOT guarantee correctness. The LLM can still ignore or misuse the provided context.

**This project's RAG is simple:** keyword-based retrieval from a JSON file. Production RAG systems use vector embeddings and semantic search — we deliberately avoid that complexity.

### 11. What is Prompt Engineering?

Prompt engineering is the practice of carefully designing the input text (prompt) to get better outputs from an LLM. In `prompt_builder.py`:

- We use a **system message** to set the LLM's role ("You are an expert competitive programming problem setter")
- We use a **user message** with grounding context + specific requirements
- We specify the exact JSON schema we want returned
- We instruct the model to return ONLY JSON (no markdown, no extra text)

These choices significantly affect output quality and parseability.

### 12. How are Transformers and PyTorch used?

- **PyTorch** is the deep learning framework. It provides tensors (multi-dimensional arrays on GPU/CPU), automatic differentiation, and the neural network building blocks. The model weights are PyTorch tensors.
- **Hugging Face Transformers** is a library built on top of PyTorch that provides pre-trained model architectures and tokenizers. We use:
  - `AutoTokenizer.from_pretrained()` — loads the tokenizer
  - `AutoModelForCausalLM.from_pretrained()` — loads the model weights
  - `apply_chat_template()` — formats messages into the model's expected input format
  - `model.generate()` — runs the forward pass and samples tokens

### 13. Local Inference vs API-based Inference

| | Local Inference (this project) | API-based (OpenAI, Groq) |
|---|---|---|
| Where model runs | Your machine | Provider's servers |
| Privacy | Data never leaves your machine | Data sent to third party |
| Cost | One-time hardware cost | Pay per token |
| Speed | Depends on your hardware | Usually faster |
| Offline | Yes, after download | No |
| Model size limit | Your RAM/VRAM | No limit |
| Setup complexity | Higher | Lower |

### 14. What are Hallucinations?

LLMs sometimes generate confident-sounding but incorrect information — wrong complexities, incorrect algorithms, buggy code. This is called hallucination. In this project:

- Grounding reduces hallucinations by providing correct facts in the prompt
- `validator.py` checks structural correctness (all fields present, correct format)
- Optional test execution checks if the Python solution runs without errors
- **However:** Even passing tests don't guarantee correctness, because the expected outputs were also generated by the LLM

### 15. What are the Evaluation Metrics?

| Metric | What it measures |
|---|---|
| `valid_json_rate` | % of outputs parseable as JSON |
| `all_fields_rate` | % of outputs with all required fields |
| `avg_generation_time` | Average seconds per generation |
| `avg_token_count` | Average tokens generated |
| `test_pass_rate` | % of Python test cases where output matches expected (internal consistency only) |

Run `python evaluation.py` to measure these across temperatures 0.1, 0.3, 0.7.

### 16. What are the Limitations?

1. **Speed:** On CPU, generation takes 2–10 minutes. A GPU reduces this to seconds.
2. **Correctness:** LLM-generated solutions and test cases are not guaranteed correct.
3. **JSON reliability:** The model sometimes generates malformed JSON, especially at high temperatures.
4. **Code execution:** Only Python solutions can be auto-executed. C++ and Java require compilation.
5. **Model size:** 1.5B parameters is small — larger models (7B+) produce better quality but need more RAM.
6. **Context limit:** Very complex problems may exceed the prompt length.

### 17. Possible Future Improvements

- Use a larger model (Qwen2.5-Coder-7B) for better quality
- Add 4-bit quantization (`bitsandbytes`) to reduce memory usage
- Implement a proper sandbox (Docker) for safe code execution
- Add C++ and Java compilation and execution
- Expand `problem_bank.json` with more topics and verified problems
- Add a problem history/save feature
- Use semantic search (FAISS) for more intelligent grounding retrieval

## Hardware Requirements

| Setup | RAM Needed | Speed |
|---|---|---|
| CPU only (FP32) | ~6 GB | Very slow (5–15 min/generation) |
| CPU only (FP16) | ~3 GB | Slow (3–10 min/generation) |
| GPU (CUDA, FP16) | ~3 GB VRAM | Fast (10–30 sec/generation) |
| 4-bit quantized | ~1 GB | Moderate |

For 4-bit quantization, install `bitsandbytes` and add `load_in_4bit=True` to `from_pretrained()` in `model.py`.

## Model Download and Offline Use

On first run, `transformers` downloads the model from Hugging Face Hub to:
```
~/.cache/huggingface/hub/models--Qwen--Qwen2.5-Coder-1.5B-Instruct/
```

After the first download, the app works completely offline. The model is ~3 GB.

To pre-download without running the app:
```python
from transformers import AutoTokenizer, AutoModelForCausalLM
AutoTokenizer.from_pretrained("Qwen/Qwen2.5-Coder-1.5B-Instruct", trust_remote_code=True)
AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-Coder-1.5B-Instruct", trust_remote_code=True)
```
